# ADR：A/B 报告交接与证据归档

- 编号：ADR-241880556-E11E12-001
- 日期：2026-11-12
- 作者：241880556 / B09

## 问题

四号需要证明 B 端既能消费 A 组当轮 EChecker 报告，也能通过 SSH 转发完成 E12 五阶段 API，并让第三方按原始字节核验产物。已有 `mode=e12` 在同一 job 内生成增量报告；API 请求没有外部报告字段。原 CI 上传动作又漏掉清单列出的隐藏文件。

## 决策

1. A→B 外部报告走 B2 的独立 `repair_report.py`：保留原始文件，用上游原始 SHA256 验证，再检查 `e11e12-1`、`incremental-check`、成功状态和目标提交。补丁在独立副本应用、构建、测试与复检；拒绝错误报告时不写补丁。
2. E12 API 继续证明本 job 的五阶段链：repair 引用本 job 的增量报告产物，不把旧固定 MD 或外部文件冒充本轮内部报告。正式交付同时记录 A→B 外部报告和 API 内部报告的不同 URI、SHA256、job/trace。
3. GitHub Actions 上传 `work/` 时包含隐藏文件，并用排除模式去掉克隆工作副本的 `.git` 元数据；下载 ZIP 后逐项按 `result.json` 清单复核 SHA256 和字节数。
4. 课程服务器在四号个人分支的独立 worktree 运行；第三人旧工作树和证据不改写。预跑与正式联调用新 job ID、证据目录、源码 SHA 和镜像 ID 区分。

## 输入输出与验证

- 外部输入：原始 `incremental-check.json`、其 SHA256、项目仓库及 target 完整 SHA、A 端 job/trace。
- B 端输出：`candidate.patch`、接收日志、构建/测试/复检日志、镜像 ID、无 MD 报告及证据包 SHA256。
- API 输入：`mode=e12` 请求、幂等键；输出：五阶段 envelope、产物 URI/SHA256、job/trace、实际候选镜像 ID。
- 已验证：四号 CI ZIP 的 368 个清单项完整；SSH 转发预跑两项成功；A 组旧归档报告的独立接收、构建与复检成功，旧报告和错误哈希被拒。
- 待验证：A 组本轮新报告的正式交接与独立复验、最终 PR 和合并后 `main` CI。

## 约束

如正式接口要求 `mode=e12` 直接消费 A 组外部报告，需先扩展 API 契约、实现和测试；现有 API 不具备此输入，不能把独立接收的结果称为 API 内部 repair 的输入。
